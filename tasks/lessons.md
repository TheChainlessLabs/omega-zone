# Lessons

- Do not ship fixed gas constants as the only gas source for zone precompile writes. Darkpool/orderbook paths can be much more expensive when they lazily initialize pair/book state; estimate gas from the connected owner and add an explicit buffer before signing raw Tempo transactions.
- Zone-private balance reads are caller-gated. When using wagmi/viem `readContract` for TIP20 `balanceOf(account)` or darkpool `balanceOf(user, token)`, always pass `account: owner` so `eth_call.from == owner`; otherwise the precompile reverts with `Unauthorized()`.
- Do not use ERC-20 `uint256` max as a Tempo access-key spending limit. T3 account-keychain spending limits are capped to the TIP-20 `u128` supply range; use `u128::MAX` at most, and avoid unnecessary approve flows that consume the key's spending limit.
- T3 scoped access-key authorization adds large intrinsic gas to the first transaction carrying `keyAuthorization`. Budget that authorization overhead separately from the contract call gas, then drop back to normal call gas after the authorization is consumed.
- When a frontend signs session-style auth tokens for private RPC access, check whether the token already carries an expiry and can be reused before accepting a per-request signing flow. Prefer cached reuse with expiry-aware refresh over prompting the wallet on every read.
- For viem contract calls, never use mixed-case address literals unless they are actually EIP-55 checksummed. Prefer lowercase `0x...` constants or normalize with `getAddress(...)` before wiring them into `writeContract` / `readContract`.
- When swapping wallet integrations, audit every `window.ethereum` dependency and every contract read without an explicit `chainId`. Custom wagmi connectors do not guarantee a global injected provider, and unscoped reads will drift onto the active wallet chain.
- Before wiring a frontend page to a precompile or system contract, check the repository tests/specs for exact chain availability and address family. In this repo, the darkpool orderbook at `0x0b...01` is a zone precompile, while the older `StablecoinDEX` at `0xDEc...` is the surface explicitly disabled on zones.
- For zone precompile writes through custom wallet connectors, prefer sending raw ABI-encoded calldata with `sendTransaction` over `writeContract` when recursion or stack-overflow errors appear. Precompile surfaces and connector-specific contract abstractions are a common fault line.
- If stack-overflow errors persist after switching to raw viem `sendTransaction`, bypass the wallet-client wrapper entirely and call the connector provider with `eth_sendTransaction` directly. That isolates failures inside connector adapters from the actual wallet/provider transport.
- If `ExecutionError.ts` still recurses after direct connector `eth_sendTransaction`, stop asking the wallet to broadcast. Request a fully prefilled `eth_signTransaction` only, then submit the signed raw transaction through the authenticated zone RPC with `eth_sendRawTransaction`.
- If `ExecutionError.ts` still recurses during `eth_signTransaction`, the wallet preview/signing path is the fault line. Authorize a short-lived, scoped local access key with `wallet_authorizeAccessKey` before signing the zone transaction; live Tempo Wallet validation requires at least one `limits` entry and at least one `scopes` entry.
- Do not rely on the provider's default local access-key signer on pre-T1C zones. The current accounts/viem stack defaults local access keys to V2 keychain signatures (`0x04`), and the zone rejects those before T1C activation.
- If direct user-approved `eth_sendTransaction` still triggers wallet-side `ExecutionError.ts` recursion, use scoped local access keys but manually hydrate the stored key with `internal_version: "v1"` before signing pre-T1C zone transactions. Do not rely on the provider's default access-key signer until the zone is T1C-active or the SDK auto-selects V1/V2 correctly.
- When authorizing zone-local access keys from a wallet that may be active on Tempo L1, always pass `chainId: BigInt(zoneChain.id)` to `wallet_authorizeAccessKey`. Otherwise the key authorization can be signed for chain `42431` and fail on the zone with `KeyAuthorization chain_id mismatch`.
- Pre-T3 zones reject `KeyAuthorization` call scopes / `allowed_calls` entirely. For local access keys before T3 activation, request limits-only authorization, reject cached scoped keys, and keep expiry short to reduce risk.
- If the wallet requires scopes for `wallet_authorizeAccessKey` while the zone is pre-T3, do not force dummy scopes. Generate the access key locally and use `wallet_connect` digest signing to sign a limits-only `KeyAuthorization` instead.
- When consuming `wallet_connect` digest signatures through connector/dialog layers, support both `accounts[0].capabilities.signature` and top-level `signature` response shapes, but still verify the returned signer address matches the connected owner before using it.
- For accounts SDK digest signing, prefer the tested `wallet_connect` shape `{ capabilities: { digest } }`. Extra login/select-account fields can trigger a connect flow that completes a prompt without returning a digest signature.
- Generated zone genesis files must include Tempo fork activation fields (`t0Time` through `t4Time`) when frontend wallet flows depend on post-T1C/T3 behavior. Missing fields boot the zone pre-T1C/pre-T3 even if the L1 network is already past those forks.
- After redeploying a zone, immediately resync frontend env from `generated/<name>/zone.json` and verify `eth_chainId` before debugging wallet/frontend behavior. A stale `NEXT_PUBLIC_ZONE_CHAIN_ID`, `NEXT_PUBLIC_ZONE_ID`, or portal address can surface as wallet execution errors that look unrelated.
- For orderbook availability questions, remember the darkpool orderbook is an in-process zone precompile, not deployed bytecode. Verify it with a direct `eth_call` to `MIN_ORDER_AMOUNT()` at `0x0b00000000000000000000000000000000000001` before changing frontend transaction code.
- When provider or viem errors show recursive `BaseError.walk` / `ExecutionError` stacks, do not read or walk those errors through normal formatter paths. Extract only plain string fields from own property descriptors and fall back to a generic message.
- Distinguish app-page errors from wallet-window errors before patching UI handling. If the recursive stack is in the Tempo Wallet popup itself, app-side message formatting changes will not fix the root cause; treat it as a wallet/runtime bug and isolate the minimal RPC payload that triggers it.
- When a wallet-runtime bug is isolated to an optional transaction path, remove that path from the UI if the protocol already supports an equivalent implicit flow. In this orderbook, explicit `createPair` is unnecessary because writes auto-create the pair.
- Tempo Wallet/WebAuthn L1 transactions can receive an `eth_estimateGas` value that is too tight once transaction-level overhead is applied to the inner call. For TIP-20 portal approvals and portal deposits from the frontend, pass explicit gas headroom instead of trusting the wallet/RPC estimate exactly.
- Do not propose rejecting self-crossing darkpool limit orders as the default fix. The product preference is that self-crossing limit orders remain valid; if the behavior is confusing, either explain/resting behavior in the UI or intentionally allow self-trades to execute.
- Do not rely on resting order ids alone for user-facing trade history. Every accepted limit-order submission needs a stable user-visible id before matching, and fill events must link maker/resting order ids with taker/submission order ids so fully filled incoming orders remain trackable.
